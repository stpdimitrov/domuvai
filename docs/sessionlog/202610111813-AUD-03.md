## AUD-03 · 2026-10-11 · identity-org — an administrator's login is nobody in the book, whichever came first (audit finding 6)

**Did** — the audit found that "an administrator's login is never tied to a party" (ADR-002's amendment, §2) held only where a tie is made: a subject already tied to a manager could be added to `DOMUVAI_AUTH_ADMINS`, and that one login would read the book and say who everybody is. Two changes. **At decision time** `Administrators.administers` answers no for any subject that carries a party — the policy's subject already holds the party the api's own record ties the login to — so a tied login keeps its party's roles and never the administrator's, however and whenever the tie was made. This alone closes the finding. **At start** a new check, `AdministratorsAreNobody`, looks every named administrator up in the record of ties, and the application does not come up if one is tied, naming the subject: it closes nothing further, it makes the mistake seen the moment it is made. The tie-time refusal (AUTH-04c) stays. ADR-002's 2026-10-11 amendment says what the mechanism now is. No migration, no endpoint; `policy` untouched.

**Rules covered** — PM-SEC-001 and PM-BOOK-006 (the administrator's role and the book stay apart); the start-up check is ADR-002's, not a rule's.

**Tests added** — `AdministratorsAreNobodyTest` (a real, small application context; no database): a deployment naming a tied login does not start and says which · one whose administrators are tied to nobody starts · one that cannot read its record does not start either · `PM-SEC-001 a login tied to a party never administers, named or not…` · `PM-BOOK-006 one login, one kind of power…` · the two services refusing a named login that carries a party. `LoginWebTest`: `PM-SEC-001 the administrator's own token is refused once the api's record ties that login to a party` — a real signed token through the real resolver. **On the real jar**, against a scratch database on this machine: starts with untied administrators · **exits at start** with the manager's subject on the list, saying so · starts again once it is taken off · starts when the same subject is tied only under another issuer. Four mutants killed: the start-up check doing nothing · a tied login still administering · the check asking under another issuer · the check stopping at the first name.

**Review** — fresh context, security-minded, six points; no way for one login to both administer and read the book was found. Taken: the guarantee rests on the resolver, and no test went through it — one now does, with a real token; the ADR said each mechanism closes a way the other leaves open, which overstated the start-up check — it now says the decision-time rule alone closes the finding, and what the check is for and costs; the start-up tests no longer carry a rule's ID; the test's shared mock is per deployment; the list of administrators is no longer readable from outside the class.

**Decisions** — mine, stated on #199: both mechanisms, the decision-time rule being the one that closes the finding · of the two powers the tied login keeps its party's — that rests on a mandate or a title, the administrator's on a line of configuration.

**Open** — **accepted with the start-up check:** a tie written for an administrator's subject by SQL or by code that does not ask stops the api at its next restart; recovery is to take the subject off the list or remove the tie — whoever can write that table can already do worse · `Logins.tie` stays public and unguarded (AUTH-04c) · who was an administrator on a past day is still not provable (ADR-002, deferred) · `EXPIRED_ACTING` and the election task are not built · the audit's other findings are not this session's.

**Read first next time** — `app/src/main/kotlin/zues/app/identity_org/Administrators.kt`, `docs/adr/ADR-002-authorization.md` (the 2026-10-11 amendment), #199.
