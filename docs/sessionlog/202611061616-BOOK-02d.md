## BOOK-02d · 2026-11-06 · registry — a member's stays cannot overlap, in the database (#446, claim #447)

**Did** — A new migration, `V202611061608__household_member_stays_no_overlap.sql`, adds to `registry.household_member` the constraint `registry.title` already has: `EXCLUDE USING gist (unit_id WITH =, party_id WITH =, daterange(valid_from, valid_to, '[)') WITH &&)`. Stays are half-open, as `current()` reads them. A NULL `party_id` never compares equal, so unnamed members are never constrained. BOOK-02c's read-then-insert check in `registerHousehold` stays, because it names the party before anything is written. Its `ponytail:` comment is gone. `RegistryService.oneStayAtATime` wraps each household insert and the move-out update in `endHouseholdStay`. It turns this one constraint's refusal (SQLState `23P01`, matched by constraint name) into an `IllegalArgumentException` naming PM-BOOK-002 and the party. The controller makes that a 400. Any other refusal is passed on unchanged. The transaction rolls back, so nothing is stored. The migration edits no rows. Checked on local Postgres: a table that already holds overlapping stays of one party fails with `could not create exclusion constraint "household_member_party_stays_no_overlap"` and the conflicting keys.

**Rules covered** — PM-BOOK-002 (one person is one member of a unit at a time), PM-FEE-008 (the headcount counts persons, so concurrent entries can't count one person twice).

**Tests added** — `BookPersistenceIT` covers these:
- `PM-BOOK-002 two concurrent entries of one party into one unit store exactly one row, the other a 400`. This is a real race. The first entry is held uncommitted. The second goes in over HTTP, gets past the read and blocks on the constraint (seen in `pg_locks`). Then it gets a 400.
- `PM-BOOK-002 a corrected move-out that runs into a later stay of the same party is a 400 and changes nothing`
- `PM-BOOK-002 against the table a party whose stay ended before the new validFrom is entered, and unnamed members are never refused`

`HouseholdPartyTest` adds `PM-BOOK-002 the table's refusal of an overlapping stay, met when a concurrent entry got past the read, is a refusal naming the rule and the party`. It also checks that another integrity refusal passes through as itself. `MoveOutTest` adds `PM-BOOK-002 a corrected move-out that runs into a later stay of the same party is a refusal naming the rule`.

**Found on the way** — Spring Data JDBC's `JdbcAggregateTemplate` raises a `DbActionExecutionException`, which is a plain `RuntimeException` and not a `DataAccessException`. It wraps the `DataIntegrityViolationException`. A `catch (DataIntegrityViolationException)` around `aggregates.insert` is never reached. The controller's `@ExceptionHandler(DataIntegrityViolationException)` matched the cause and answered 409. So the catch is on `RuntimeException` and reads the root `SQLException`. `MandateAdministration` catches DIVE directly because it writes through `JdbcTemplate`.

Second, it is named for PM-FEE-008 as well and checks that the headcount stays 1. Third, the migration's comment carries the query that finds overlapping rows. I re-ran the race test locally (10/10) and re-ran the drop-the-constraint mutant: killed.
